# Employee and admin controls: release review

These are acceptance gates for the local experience described in `handoffs/04-friend-sol.md`, not a claim that the controls are implemented. Run them with synthetic chat content, separate employee and admin sessions, and a fake adapter that records attempted actions. Record the build, observed result and evidence for each gate; an untested gate is not a pass.

| Gate | Exercise | Required result |
| --- | --- | --- |
| Employee status | Start a task, request clarification, then disconnect the adapter. | The employee can tell what is running, what input is needed, and when status is unknown. A disconnect is not reported as completion. |
| Pause, stop and resume | Pause during work with a second action queued. Refresh, then resume explicitly. Repeat with Stop instead. | Pause acknowledges the request immediately, blocks new dispatches and identifies any action already in flight. Show “Paused” only once work has settled. Refresh does not resume work. Resume does not repeat completed actions. Stop ends the run and discards its queued work; starting again requires a new run. |
| Admin authorization | From employee, signed-out and expired admin sessions, directly request policy, context and pace changes and access to observation. Repeat from an authenticated, authorized admin session. | The local service checks every request, not just panel visibility. Denials reveal no protected content and leave settings unchanged. Observation is off by default, visible to the employee when active, and view-only: it cannot send chat, act as the employee or override pause. |
| Local access control | Inspect the OS pipe permissions, attempt access as an unrelated local user, and check for TCP listeners and readable private files. | Only the authorized local identity can use the pipe. No TCP listener, including loopback, is available. Unrelated users cannot mutate settings or read private transcripts, session secrets or configuration. |
| Reversible changes | Preview and cancel an edit; apply changes to policy, context and pace; undo them and reload. Attempt undo after another admin has edited the same setting. | Cancel writes nothing. Before applying, show old and new values and when they take effect. Undo restores the prior effective setting without silently overwriting a newer edit. Record who changed what and when without logging secrets or chat content. Explain that restoring a setting cannot undo completed external actions. |
| Accessibility | Using only the keyboard, pause a run, answer a clarification, cancel an admin edit and undo a saved change. Repeat with a screen reader and at 200% zoom. | Controls remain visible, named and operable; focus is visible, follows a logical order and returns to the initiating control after dialogs. State and errors are conveyed in text, not color alone. Status changes are announced without moving focus or reading every streamed token. |

Do not sign off if a denied request changes state, if work starts while paused, or if an employee cannot reach Stop with the keyboard. For a failure, attach the smallest synthetic reproduction and the expected and observed outcomes; rerun that gate after the fix.
